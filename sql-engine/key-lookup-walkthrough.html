Reading the diagram

Each box is one 8 KB page

page 1:900 is the page address: file 1, page 900. Child pointers inside other pages use exactly this address.

  • root is the single entry point. Its address is stored in the system catalog.
  • int (intermediate) pages only route the search downward.
  • leaf pages hold the actual index entries. The double lines between leaves are the previous/next page pointers.

Rows in IX_t_secondary_id

The index is non-unique, so SQL Server appends the clustering key id. Every entry becomes a pair (secondary_id, id), sorted by secondary_id first, then id.

RowMeaning
(4,17)Leaf entry. A row with secondary_id 4 exists, and its id is 17.

Why the seek starts at (4, −∞)

The query fixes only the first half of the key. All entries for secondary_id = 4 sit next to each other in key order, but the query cannot know which id comes first. Here is the whole leaf level laid out in sorted order:

(1,8)1:910(1,330)1:910(2,12)1:910 (2,40)1:911(2,77)1:911(3,5)1:911 (3,5120)1:912 start
(4,−∞) (4,17)1:912(4,203)1:912(4,9551)1:913 stop (5,88)1:913(5,412)1:913
  1. The seek needs the position just before the first 4. Written as a pair, that position is "secondary_id 4, with an id smaller than any real id", which is (4, −∞). −∞ is not stored anywhere. It is notation for "lowest possible value of the unknown column".
  2. Pairs compare left to right, like words in a dictionary. The first column decides unless it ties, and only then does the second column matter. So (4, −∞) is greater than (3, anything) and less than (4,17) and every other real (4, …).
  3. The seek descends to that position, then reads forward until the first column exceeds 4.

In the actual execution plan, the Index Seek's properties show Seek Keys[1]: Prefix: secondary_id = 4. A "prefix" seek on the leading key column is the same operation shown here as (4, −∞).
